# 调研类型扩展指南

本技能以产品竞品调研为核心高频场景，同时支持多种调研类型。每种类型在核心报告模板基础上灵活裁剪和扩展，并配合商业化分析与战略分析框架。知识体系整理类不套用竞品模板，独立结构见第七节。

## 调研类型总览

| 类型 | 核心问题 | 主模板 | 补充框架 |
|------|---------|--------|---------|
| 产品竞品调研 | 竞品是什么？能做什么？比我好在哪？ | report-template.md | commercial-analysis.md |
| 技术选型 | 选A还是选B？各有什么取舍？ | report-template.md（裁剪） | 下方框架 |
| 行业研究 | 这个行业怎么样？有机会吗？ | report-template.md（裁剪） | strategic-frameworks.md |
| 市场分析 | 市场有多大？谁占多少？我能进吗？ | report-template.md（裁剪） | commercial-analysis.md + strategic-frameworks.md |
| 开源生态调研 | 开源项目活不活？能不能用？要不要用？ | report-template.md（裁剪） | 下方框架 |
| 商业化评估 | 这门生意赚不赚钱？怎么赚？ | commercial-analysis.md | strategic-frameworks.md |
| 知识体系整理 | 这个领域有什么？关键概念怎么理解？全景长什么样？ | 下方第七节结构 | 无（自含） |
| **全栈技术选型** | **做这个产品该用什么技术栈？每一层怎么选？为什么？** | **下方第八节结构** | **按产品类型加载对应矩阵** |

## 一、产品竞品调研（核心高频）

**适用场景**：了解竞品能力边界、寻找差异化定位、支撑产品规划和立项决策。

**报告结构**：完整骨架见 `report-template.md`，核心章节如下：

```
一、调研框架总览        → 覆盖维度一览，让读者秒懂报告结构
二、市场与行业背景      → 市场规模/驱动力/技术演进
三、国内产品图谱        → 云厂商 + 专精型企业，含能力矩阵
四、海外产品图谱        → 云厂商 + 传统厂商 + 新兴工具，含能力矩阵
五、垂类行业场景        → 按行业拆解应用场景和代表产品
六、核心差异深度分析    → 定位/技术路线/交付模式三维对比
七、技术趋势与洞察      → 方向研判，非事实罗列
八、竞争格局与核心发现  → 梯队划分 + 精炼结论
```

**关键执行要点**：
- 每个产品用统一的单产品表格（产品名/核心能力/特色能力/输出格式/部署方式/定价/核心差异）
- 能力矩阵用 ✅/❌/部分/未明确 标注，"部分"必须有脚注说明
- 竞争格局用ASCII框图按梯队可视化
- 报告中自身产品（如有）单独一节，放在国内产品图谱中，便于对标
- 核心发现控制在10条以内，每条一句话，有观点不堆砌
- **结论先行**：每章末尾必须有编号结论列表，每个厂商小节末尾有星级评分和一句话定位，让读者可跳过细节直接看判断
- **多维表格+横向矩阵双输出**：厂商逐一评估用维度表格展示细节，章节末尾用横向对比矩阵汇总关键维度，两种形式互为补充
- **报告结构按主题选择**：当调研聚焦"能力×场景"交叉评估时，优先用场景驱动结构（模式B），而非默认的地域驱动结构（模式A）

#### 场景驱动结构骨架（模式B）

适用于"某核心能力在不同场景下表现如何"类调研：

```markdown
一、核心能力定义与分层      → 定义能力边界、技术核心、产品化难度
二、核心能力全景            → 全厂商总表 + 各层竞争格局分析 + 结论
三、场景一：{名称}          → 需求画像 → 各厂商逐一评估 → 横向对比 + 结论
四、场景二：{名称}          → 同上
五、综合分析                → 定价格局 + 国内外差异 + 技术趋势
六、最终结论                → 编号列表，10条以内，每条一句话有观点
```

#### 厂商逐一评估模板（模式B第三/四章专用）

每个厂商用统一的"维度表格+优势/局限"结构，维度行标签根据场景定制：

| 场景 | 维度行 |
|------|--------|
| 数据清洗 | 解析、还原、再编辑、批量/离线、成本、私有化 |
| RAG知识库 | 解析、还原、Chunk策略、溯源、集成、成本 |

MD格式示例：
```
#### 厂商名 ——核心定位标签 ⭐⭐⭐⭐⭐
| 维度 | 能力表现 |    | 维度 | 能力表现 |
|------|---------|    |------|---------|
| 解析 | ...    |    | 成本 | ...    |
| 还原 | ...    |    | 私有化 | ...  |

核心优势：...    核心局限：...
场景适用度：⭐⭐⭐⭐
```

HTML版用 `.vc` 厂商卡片组件渲染（详见 `style-guide.md`），禁止使用 `h4 + ul + p局限` 的碎片化堆叠。

**配合框架**：
- 定价/商业模式 → `commercial-analysis.md` 第一、二节
- 差距分析/行动建议 → `strategic-frameworks.md` 第二、六节

## 二、技术选型调研

**适用场景**：为团队选择技术方案（数据库、框架、中间件、云服务等）。

**报告结构**（在核心模板基础上裁剪和替换）：

```markdown
# {技术领域}技术选型调研

## 一、选型背景与需求
### 1.1 业务场景与核心需求
### 1.2 非功能需求（性能/可用性/安全性/合规）
### 1.3 团队约束（技术栈匹配/运维能力/预算）

## 二、候选方案图谱
### 2.1 商业方案
### 2.2 开源方案
### 2.3 自研方案

## 三、方案深度评估
### 3.1 功能匹配度矩阵
| 需求项 | 方案A | 方案B | 方案C |
|--------|:---:|:---:|:---:|
| {需求1（必选）} | ✅ | ✅ | ❌ |
| {需求2（重要）} | ✅ | 部分 | ✅ |
| {需求3（加分）} | ❌ | ✅ | ✅ |

### 3.2 性能Benchmark（标注测试条件）
### 3.3 架构与设计理念对比
### 3.4 学习曲线与文档质量
### 3.5 生态与集成兼容性
### 3.6 许可证与法律风险

## 四、综合评估
### 4.1 加权评分矩阵
| 维度 | 权重 | 方案A | 方案B | 方案C |
|------|:---:|:---:|:---:|:---:|
| 功能匹配 | 30% | 8 | 7 | 5 |
| 性能 | 25% | 7 | 9 | 8 |
| 生态 | 15% | 9 | 6 | 4 |
| 运维复杂度 | 15% | 6 | 5 | 9 |
| 成本 | 10% | 5 | 7 | 9 |
| 许可证 | 5% | 8 | 9 | 10 |
| **加权总分** | 100% | **7.25** | **7.05** | **6.25** |

### 4.2 风险与缓解策略

## 五、推荐方案与路线图
### 5.1 首选方案及理由
### 5.2 备选方案及切换条件
### 5.3 实施路线图（POC → 试点 → 全面推广）
```

**关键差异**：
- 以需求为锚点，功能匹配度矩阵替代能力矩阵
- 加权评分矩阵替代简单的✅/❌对比
- 增加"风险与缓解"和"实施路线图"

## 七、知识体系整理与学习研究

**适用场景**：系统性梳理某领域的知识全景，让读者建立清晰认知框架。常见触发：全景图、知识体系、基础知识、学习路线、入门指南等。

**与竞品调研的核心差异**：竞品调研目的是"支撑决策"，知识整理目的是"建立理解"。因此：
- 不需要商业化分析、战略推导、竞争格局
- 需要**术语双栏解读**：每个关键术语同时给出正式定义和通俗理解
- 需要**层次化结构**：从概览到细分，从基础到进阶
- 实践指引**按需裁剪**：只有当领域涉及"选型/方案选择"时才出实践指引章节，纯知识科普可不加

**报告结构**（通用骨架，各章节按领域特点灵活裁剪）：

```markdown
# {领域名称}知识体系全景图

## 一、领域概览
### 1.1 什么是{领域}——一句话定位
### 1.2 核心问题与边界

## 二、核心概念层
### 2.1 核心概念（正式定义 + 通俗理解双栏表格）
### 2.2 底层原理/基础逻辑

## 三、主要分支逐项展开
### 3.1 {分支1}（子概念表格 + 关键要点）
### 3.2 {分支2}
### 3.N {分支N}

## 四、关键实体/工具/方法全景
> 章节标题按领域调整：技术领域用"工具与框架"，学术领域用"理论与方法"，行业领域用"代表机构与产品"
### 4.1 代表实体对比（正式定义 + 通俗理解 + 适用场景）

## 五、实践指引（可选，仅当领域涉及方案选择时加入）
> 技术领域→选型参考；方法论领域→应用场景指南；行业领域→入门路径建议
| 场景/需求 | 推荐方案 | 理由 |

## 附录：核心概念速查表
| 术语 | 正式定义 | 通俗理解 | 所属分支 |
```

**关键执行要点**：
- **术语表格统一三栏**：`术语 | 正式定义 | 通俗理解`，缺一不可。正式定义给"它是什么"，通俗理解给"一句话类比"
- **正式定义标注全称**：有缩写的标注全称（如 REST = Representational State Transfer）；无缩写的写完整名称即可，不强求英文
- **通俗理解用日常类比**：一句话说清"干嘛的/为什么存在"，避免学术黑话套娃
- **章节标题灵活适配领域**：第四章标题按领域调整（技术→工具与框架；学术→理论与方法；行业→代表机构与产品），不强套技术领域结构
- **实践指引按需裁剪**：纯知识科普（如"量子物理基础"）无需选型指引；涉及方案选择（如"全栈开发技术栈"）则加入
- **信息来源**：以官方文档、权威教材、百科、学术综述为主，数据同样需可验证
- **Phase 4 战略分析可跳过**：知识整理无战略推导需求
- **Phase 5 门禁轻量版**：核查术语定义准确性 + 通俗理解是否误导 + 信息是否过时

## 八、全栈技术选型调研

**适用场景**：为即将开发的产品（App、Web、SaaS平台、商业化系统、后台管理系统等）设计完整的技术体系方案，包含前端框架、后端架构、数据库、账号体系、基础设施等全维度选型。

> **⚠️ 为什么需要这个类型**：全栈技术选型是AI最容易"乱答"的场景——倾向于按习惯推荐同一套技术栈（如"React + Node + PostgreSQL"），而忽视产品类型、团队规模、商业化需求、部署环境的差异。本类型通过强制需求锁定和逐层拆解，避免默认选型，每一层的选择必须回答"为什么选这个，不选别的"。

### 第一步：产品画像锁定（必须先完成，禁止跳过）

在开始任何技术选型之前，必须明确以下信息（信息不足时主动向用户确认）：

| 维度 | 说明 | 示例 |
|------|------|------|
| **产品类型** | 决定技术栈方向的根本 | ToC App / ToB SaaS / 内部管理系统 / 开发者工具 / 数据平台 / 内容平台 |
| **访问终端** | 决定前端技术栈选择 | Web only / Web+移动端 / Native App(iOS/Android) / 小程序 / 桌面端 / 多端并存 |
| **用户规模** | 决定架构复杂度 | 初期<1000 / 中期1万级 / 大规模100万+ |
| **团队规模与技术背景** | 决定技术选型的可落地性 | 1-3人独立开发 / 5-10人小团队 / 20人+工程团队 / 外包交付 |
| **商业化模式** | 决定账号体系和计费模块 | 免费工具 / 付费订阅 / 按量计费 / 私有化交付 / 开源商业双轨 |
| **数据敏感度** | 决定部署方式和合规要求 | 公有云部署 / 需支持私有化 / 数据合规（GDPR/等保） |

#### 商业化基础设施选型

付费/订阅功能是商业化产品绕不开的选型，需根据目标市场选择：

```markdown
| 维度 | 国内市场 | 国际市场 |
|------|---------|---------|
| **支付网关** | 微信支付 / 支付宝 / 银联 | Stripe（首选）/ Paddle / LemonSqueezy |
| **订阅管理** | 需自建或用支付平台能力 | Stripe Billing / Paddle / Chargebee |
| **发票/合规** | 腾讯云/阿里云开票API | Stripe Tax / Quaderno |
| **用量计费** | 自建计量 + 支付平台代扣 | Stripe Metered Billing / Orb |
| **LemonSqueezy适用** | 不适用（无国内支付） | 独立开发者/简单付费墙 |
| **Paddle适用** | 不适用 | 需Merchant of Record（代收税务） |
```

> **国内产品注意**：如需同时支持国内+国际市场，支付体系必须双轨设计，不可用单一方案兼容。

### 关键执行要点

- **禁止默认推荐**：每个维度的选择必须明确说明"为什么选这个"，给出至少一个"为什么不选XXX"的对比说明
- **MVP vs 正式版分层**：对于初创产品，必须给出"MVP阶段可简化的选择"和"规模化后的升级路径"，避免过度设计
- **锁定风险标注**：凡是引入托管服务（BaaS/第三方Auth/SaaS数据库），必须标注"锁定程度"和"迁出成本"
- **国内/国际双轨**：支付、账号、基础设施需明确区分国内外差异，不得混用
- **选型一览表必须输出**：报告末尾必须有"全栈选型总览一览表"，一行一个层级，让读者秒懂整体技术决策
- **Phase 4 战略分析可简化**：本类型不需要竞争格局分析，Phase 4 替换为"技术风险 + 团队可落地性评估"
- **Phase 5 门禁调整**：定价核查替换为"官方文档版本核查（框架版本/托管服务限制是否现行有效）"
